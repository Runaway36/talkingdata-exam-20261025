## 设置与结果

业务代码为 `4a23820622cbfa662ca6a55a72bc8a03f0d54025` 对应的 v2；汇总程序核对了六次运行的业务模块 SHA256 与当前代码一致。每模型、每 seed 一次运行。

- DeepSeek：官方 API 返回模型标识 `deepseek-flash`，thinking=disabled。
- 本地模型：`Qwen2.5-1.5B-Instruct`，CUDA BF16，既有离线权重。
- 统一 Harness：文本 JSON 单动作协议，只提供业务 API；不提供终端、代码执行或计算器，不提供参考答案和验证器。
- 统一预算：temperature=0，每轮最多 1024 输出 token，最多 12 轮。不同模型的 tokenizer 不同，这不是严格相等的计算量预算。
- 六次运行均产生了可解析、符合答案 schema 的最终结果；均未达到输出截断或轮次上限。schema 合法不代表业务正确。

“整题正确”要求事件集合、每个事件的等级/服务集合/数量、优先级和快照均与独立 SQL oracle 一致，忽略事件列表与服务列表的排列。该指标由汇总脚本计算，没有改变训练接口的 reward。数量与服务集合指标以应输出的 9 个目标事件为分母，遗漏记错；两类模型还都存在额外事件，不能只看这两个字段指标判断交付完整性。

参考程序是确定性解法，不是第三个受测 LLM。它通过业务 API 获取数据，再用 Python 循环计算；三例均与 SQL oracle 一致。seed 17 还完成了不导入参考解和验证器的 [原始 API 记录独立逐桶复算](seed17-independent-calculation.md)：AUTH=48，DB=143+31=174，PAY=120，优先级 DB、PAY。此核对不证明全数据分布均无错误。

## 可从轨迹确认的差异

DeepSeek 每例发起六次查询，取得了必要业务来源，并有额外查询。seed 17 的两个 metrics 请求及返回已逐条对照当前 API，六份工具返回均原样进入最终模型请求。最终把目标数量写成 0 的内容已经存在于原始模型响应中，不能归因为保存或评分时被清零。AUTH 第一桶单独就有 `19 - 1079 * 100 // 10000 = 9` 的正贡献，可以直接反证零数量答案。记录不能确定模型内部是在计算还是组织答案阶段出错。

Qwen 每例先生成了不符合单动作封装的回答，收到一次固定协议反馈后查询 `list_alerts`，随后直接提交最终答案。三例都没有查询事件服务关系、服务资料、请求指标或维护记录。seed 17 将 `host-db` 等资源 ID 填入服务字段。其最终数量与服务集合均不正确；这是预算内实际输出的结果，不能推出模型在其他提示或 Harness 下也必然失败。

当前可观察到工具选择和服务识别的差异；两者的核心数量都未算对。三个固定实例不足以证明稳定通过率、固有难度或训练收益，也没有证明更强的 DeepSeek 配置能达到什么水平。

## 奖励解释与设计审阅

独立上下文 AI 的 [静态设计审阅](../design-review/independent-review.md) 指出了权重解释及固定结构捷径。汇总程序实际执行了两份构造答案，复核了其中的奖励问题：

- 三个数量全写 0、其他字段和排名全部正确：reward=0.833333。
- 正确答案额外添加一个虚假事件：reward=0.964286。

两者都未得满分，但说明现有连续奖励不能解释为业务正确率。因此上述结果同时列出严格正确和核心字段正确数；当前权重尚未按业务价值校准。

实际生成器主要随 seed 改变指标数值，事件服务关系、基线和维护结构基本固定。长期反复训练可能记住固定结构并减少必要查询；这是一项静态识别出的设计风险，当前轨迹没有证明模型已经采用这种策略。审阅来自另一个独立上下文的 AI，不是人工业务认可或另一家模型的评测。

本轮只做模型试跑、证据核对及审阅记录；未修改业务任务、评分定义，也未操作考试交卷。
