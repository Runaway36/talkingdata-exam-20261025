# 独立上下文设计审阅

日期：2026-10-25。范围：当前源码、README、docs、tests 的静态阅读；未运行测试、Docker、模型或训练，未操作 Git，未修改任务实现。以下行号对应本次阅读版本。优先级 P1 指影响训练任务的有效性或分数解释，P2 指影响难度论证或后续扩展。

总体判断：这是边界清楚、计算链条完整的合成业务分析任务，接口与验证器的职责划分较好。最需要补强的是“跨实例仍必须获取多源数据”的设计，以及奖励数值对业务正确性的表达。当前代码足以支持“具备跨 API 关联计算”，不足以支持“已经证明对模型有有效挑战”。

## 已查到的设计基础

- **业务口径基本自洽。** 任务明确统计服务调用异常失败次数，并排除去重用户数、金额和跨根因分摊；完整桶、维护状态、基线取整、零下限、截止时活动告警均有明确规则（`alert_rlvr/config.py:33-44`）。SQL 落实相应筛选、关联和维护排除（`alert_rlvr/verifier.py:122-159`）。这能构成一个确定性业务口径，但异常失败与事件之间的因果关系是输入假设，不是本题推断出的现实因果结论。
- **多源关联有真实计算意义。** 告警提供事件及等级，关系表提供服务与影响区间，服务资料提供环境与基线，指标提供计数，维护决定排除桶；没有单个公开 API 直接返回总额或排名（`alert_rlvr/environment.py:118-150`、`examples/reference_agent.py:23-79`）。
- **验证器有独立实现和可解释分项。** 真值采用 SQL，参考解采用业务 API 加 Python 循环，评分入口只收任务和答案（`alert_rlvr/verifier.py:116-206,214-275`、`examples/reference_agent.py:23-81`）。手算 fixture 覆盖取整、维护、零下限及并列排序（`tests/fixtures.py:53-55,79-115`）；这是静态可见的测试设计，本审阅没有复核其执行结果。
- **接入说明易于定位。** Docker 默认入口确实指向 demo，挂载所需 `PYTHONPATH` 已设置；Harness 明确由可信控制器评分（`Dockerfile:8-13`、`examples/harness_integration.py:8-17`）。这支持“接入结构清楚”，不等同于本审阅已经验证容器运行成功。

## 最重要的四项发现

### 1. P1：实际 seed 分布存在记忆结构、只查一个 API 的捷径

**代码事实：** 服务环境及基线、事件服务关系、告警状态及等级、维护记录均为固定列表（`alert_rlvr/data.py:56-114`）。seed 改变请求数、失败数及噪声字段（`alert_rlvr/data.py:115-143`），不会改变上述结构。有效事件一直是 AUTH、DB、PAY，贡献服务集合与严重等级固定。

**静态推断：** 对反复接触该分布的策略，只需记住哪些服务、哪些桶、哪些基线有效，再调用一次 `get_request_metrics`，即可重算任一 seed 的答案；这条路径无需读取 SQL 或评分器。初次接触未知快照时五类数据都有业务意义，但多次训练后的“至少三类 API 仍然必要”没有由当前生成分布保证。

`tests/test_reward.py:241-253` 的反事实测试修改的是手算 fixture 中的关系、基线、指标和维护；它验证业务公式依赖这些信息，不能证明实际 seed 生成器会产生这些变化，也不能排除记忆结构的策略。

**优先建议：** 同一业务场景内让关系、生产环境/基线、维护状态与覆盖、活动告警等决定答案的信息也随实例变化，避免 ID 名称固定暗示答案；之后在未见实例上比较完整查询策略与“固定结构＋只查指标”策略。是否已有模型采用捷径，需要实测，不能由此断言。

### 2. P1：奖励高分不一定代表核心业务量算对，误报惩罚也较轻

**代码事实：** 事件覆盖、三个明细字段和排名分别占 25%、50%、25%；severity、service_ids、excess_failed_requests 在明细分内等权，数量只占总奖励的六分之一（`alert_rlvr/config.py:18`、`alert_rlvr/verifier.py:18-20,239-261`）。数量为零仍是合法协议输入（`alert_rlvr/verifier.py:100-103`）。

**由公式直接推导，未运行：**

- 三个事件的 ID、severity、service_ids 和 priority 全对，三个数量都填 0，奖励仍为 `0.25 + 0.50×(6/9) + 0.25 = 5/6 ≈ 0.8333`；这份答案还违反了“只输出正影响事件”的业务含义。
- 三个事件全部正确，再增加一个虚假事件且保持正确 priority，奖励为 `0.25×(6/7) + 0.50 + 0.25 = 27/28 ≈ 0.9643`。

这不是“错误答案得满分”的漏洞；它说明连续奖励偏向结构与识别信息，不能解释为业务正确率或可交付程度。固定结构又使其中若干高权重信息更容易记忆。现有反例测试主要确认“低于 1”，不约束严重错误应降到什么程度（`tests/test_reward.py:76-94`）。

**优先建议：** 将严格正确率、数量正确率、误报率与平均 reward 分别报告；如要用于训练，再依据业务目标校准数量权重、误报惩罚和内部一致性处理，保留部分奖励以提供学习信号。无需仅为让错误例低分而机械调整权重。

### 3. P2：主要难度是规则执行与算术，数据源选择和约束发现较弱

**代码事实：** 任务直接列出了所需数据源、去重键、完整桶条件、维护例外、计算公式及完整排序规则（`alert_rlvr/config.py:35-43`）。冗余工具描述还直接提示主机指标不衡量失败请求（`alert_rlvr/environment.py:27`）；API 文档将两项工具明确称为冗余（`docs/API.md:24-25`）。

**推断及边界：** 当前有真实的跨表计算和边界判断，不能称为无难度；但“有七个工具”“有多个边界”本身不能推出模型挑战性。若模型仅收到 task 与 schema，已经获得相当完整的解题路线。更准确的定位是：明确业务规则下的多源汇总、筛选与精确计算，而不是让模型发现未明说的业务约束。

**需实测：** 固定模型、工具预算和输入边界，使用多个未见实例保存最终答案、分项奖励与具体错误。对照错误应能区分关系关联、时间边界、维护判断、算术和排序；先观察是否真的触发目标错误，再决定是否需要增加难度。不要通过隐藏评分规则制造挑战。

### 4. P2：配置集中了一部分参数，时间与数据生成尚未完全解耦

**代码事实：** 窗口、桶长、基数、top_k 在 `config.py` 中集中定义（`alert_rlvr/config.py:6-18`），但数据生成器仍硬编码日期、六个桶、五分钟及 10000（`alert_rlvr/data.py:9-10,117-133`）。任务文本和 oracle 会跟随 config，数据生成器不会自动跟随所有配置。`docs/CONTRACT.md:60` 已诚实说明修改时间范围需要同步改生成器。

**影响：** 对冻结的单任务版本，这是可接受的边界，不是当前默认配置的计算错误；如果交付要求把“配置解耦”理解为更换窗口或桶长即可运行，则现有实现只部分满足。

**建议：** 明确哪些配置可独立调整，哪些属于必须升级版本的业务契约。若确需配置化时间，再让生成器从同一时间配置派生；不必为固定场景扩成通用监控平台。

## 结论边界

本审阅未发现需要把整套设计推倒重来的依据；关联计算、确定性评分和交付接口的核心结构成立。优先处理顺序应是数据变化是否保留必要依赖、奖励如何解释，然后才是模型难度实证与更广泛的配置能力。本报告不以项目自述的测试通过或容器成功作为独立验收结论。

这只是独立上下文 AI 审阅，不是人工业务认可，不是实际模型难度证据，也不证明训练收益。
